# Initial Guru model policy — architecture locked

GPT-6 Luna is the everyday/base Guru model via OpenAI direct API and a dedicated API key. Claude Sonnet 5.5 is the higher-cost escalation target. These are the user's chosen models, not assertions that either API identifier or account access has been verified. The escalation provider/authentication route is intentionally unset; do not infer it from the model's name or substitute another model silently. Provider and model selections remain replaceable configuration.

Gurukul owns escalation authority. Hermes can submit a request with a reason and evidence references, but cannot choose an escalation endpoint, receive escalation credentials, execute that call or trigger automatic fallback. Proposed flow: request -> Gurukul policy decision -> bounded one-call grant -> runtime-selected worker -> result -> recorded outcome. A grant must identify the model/route, task, expiry and budget; replay or task/model mismatch is refused. Before activation, concrete grant/budget rules and enforcement tests are required. This commit records architecture only; it does not claim working routing enforcement.

Initially defined reasons are difficult pedagogical reasoning, ambiguous pedagogical reasoning, qualitative gate assessment and repeated misconception. Every request must cite the concrete problem and evidence; a reason label by itself is insufficient. Any other case requires an explicit versioned policy addition. Numerical thresholds and spending limits have not been invented. Requests lacking configured authorization conditions, route or budget remain blocked and recorded. No automatic upgrade on timeout, model unavailability or learner frustration.

Gate escalation supports qualitative evaluation only. Models cannot override deterministic failures or grant mastery/progression; those remain Gurukul decisions. Preserve the base answer and escalation answer as distinct evidence so later calibration can assess whether escalation changed the diagnosis, reduced repeated errors or improved later retrieval.

Record both approved and denied requests, with reason, evidence, policy version and authorization. For actual calls retain provider, requested/resolved model, provider request ID, timing, token usage, estimated and actual cost (where supplied), pricing source/version, outcome and response/evaluation references. Missing usage or price data stays null with an explicit status. Never report fabricated zero cost. Token categories can overlap; do not sum cached/reasoning tokens blindly. Calibration must distinguish observed costs from estimates and eventual learner results from model self-assessment.

All call metadata, responses and learner evidence stay under ignored local runtime state. Credentials never enter policy files, Git or chat. The first GURU-004A/B acceptance turn remains base-model only. Escalation connectivity is not a prerequisite for that turn. skip_memory=True is an isolation-milestone control, not the final Guru design; Gurukul owns long-term learner continuity and supplies scoped context.

Next prerequisite remains the Mac preflight inventory already requested. GURU-003 Mac acceptance is complete and is not repeated.
